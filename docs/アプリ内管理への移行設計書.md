作成日: 2026-08-21

# 1. 変更の背景

## 1.1 現行方式の課題（運用して判明したこと）

【運用実績】既存設計（v2.0以降）では「Excelが唯一の正、Webは表示層」という方針を採り、次の運用としていました。

```
管理者がExcelを編集 → アップロード → 確認画面 → 確定 → 厨房タブレットに反映
　　　　　　　　　　　　　　　　　　　　　　　↑
　　　　　　管理者不在時のみ、厨房が当日〜2日後の範囲で直接入力（kitchen_overrides）
```

実運用の結果、次の2つの課題が明確になりました。

**課題1: 変更のたびにExcelを開いて編集・アップロードする手間**

欠食・臨時喫食の連絡は日々随時発生します。そのたびにExcelファイルを開き、行を追加し、保存し、管理者画面からアップロードし、確認画面で確定する、という一連の操作が必要でした。アプリ内で直接登録できれば1タップで済む作業に、毎回この手数がかかっていました。

**課題2: 厨房の緊急入力が、管理者の転記漏れで失われる構造的リスク**

【運用実績】より深刻なのはこちらです。厨房職員が数日間にわたり細かく食数を修正してくれていた場合、管理者がそれらをExcelへ転記する前に古いExcelをアップロードすると、確認画面での対応を誤れば厨房の入力内容が失われます。設計上は「アップロード時に競合を1件ずつ確認する」仕組み（§0.5）で防いでいましたが、**最終的な安全性が管理者の注意力に依存している**点は変わりません。人間の記憶と手作業に依存する仕組みは、いずれ必ず抜けが生じます。

## 1.2 変更の方針

【要件指定】食数記録・利用者名簿の管理を、**Excelからアプリ内管理へ全面的に移行**します。

- 管理者は、アプリ内で日付の制限なく食数（欠食・臨時喫食・職員食・来客）を編集できる
- 厨房職員も、**日付の制限なく**同様に編集できる（変更時は連絡を必須とする運用でカバー）
- 利用者名簿（氏名・区分・食形態・標準喫食パターン）もアプリ内で管理する
- **週間献立表・勤務表は対象外**。他システムの出力であり貴施設が手入力するものではないため、引き続きExcelアップロード方式を維持する

これにより、Excelファイル自体がシステムの管理対象から外れます（貴施設が個人的に控えとして使う分には自由ですが、システムは参照しません）。

# 2. 変更後のアーキテクチャ

## 2.1 データフロー

```
【変更前】
Excel（唯一の正） → アップロード・解析 → Supabase → タブレット表示
                                        ↑
                        厨房の緊急入力（当日〜2日後・別テーブル）

【変更後】
管理者PC・スマホ ─┐
                  ├→ Supabase（唯一の正）→ Realtimeで即時反映 → タブレット表示
厨房タブレット   ─┘
（どちらも日付制限なく直接編集）

※週間献立表・勤務表のみ、従来通りExcelアップロード（変更なし）
```

## 2.2 「唯一の正」の所在が変わる

これが今回の変更の本質です。設計書v1系（Supabaseが正）→v2系（Excelが正）→今回（再びSupabaseが正）という経緯になりますが、v1系と今回とでは前提が異なります。v1系の設計時は「厨房職員が電子機器に不慣れなため、入力を最小限にしたい」という懸念からExcel主導を選びましたが、実際に運用してみると、**厨房職員は1タップ方式のUIで問題なく入力できており**、むしろ管理者側のExcel往復の手間が課題になりました。この実績を踏まえた方針転換です。

# 3. データベース設計の変更

## 3.1 廃止するテーブル

| テーブル | 廃止理由 |
|---|---|
| `kitchen_overrides` | 「Excelとは別枠の当日限定上書き」という概念自体が不要になる。厨房職員も`meal_exceptions`本体に直接書き込む |
| `kitchen_visitor_overrides` | 同上。来客数も`daily_meal_extras`本体に直接書き込む |
| `import_batches` | 食数Excelのアップロード履歴。食数Excelを廃止するため不要 |

【設計提案】これらのテーブルは、移行完了後に**データを確認した上で削除**します。移行直後は残しておき、想定通り動作することを確認してから削除する二段階方式を推奨します（万一の切り戻しに備えるため）。

## 3.2 変更するテーブル

### meal_exceptions（欠食・臨時喫食）

| 項目 | 変更前 | 変更後 |
|---|---|---|
| 書き込み権限 | service_role専用（Excel取込処理のみ） | admin/kitchen とも直接書き込み可、**日付制限なし** |
| `source_batch_id` | import_batchesへのFK | 廃止（またはnull許容のまま残置） |
| `created_by` | （なし） | 追加。誰が登録したかを記録 |

RLSポリシー:
```sql
-- 変更後
create policy meal_exceptions_select on meal_exceptions
  for select to authenticated using (true);
create policy meal_exceptions_insert on meal_exceptions
  for insert to authenticated with check (true);
create policy meal_exceptions_update on meal_exceptions
  for update to authenticated using (true) with check (true);
create policy meal_exceptions_delete on meal_exceptions
  for delete to authenticated using (true);
```

【設計提案】日付制限を設けない代わりに、**変更履歴（change_logs）への記録を確実に残す**ことで追跡可能性を担保します。既存の監査トリガーをそのまま活用します。

### daily_meal_extras（職員食・来客）

同様に、admin/kitchen とも直接書き込み可・日付制限なしに変更します。

### residents / resident_default_meals（利用者名簿・標準喫食パターン）

| 項目 | 変更前 | 変更後 |
|---|---|---|
| `residents`の書き込み | service_role専用（Excel取込） | **admin のみ**直接書き込み可 |
| `resident_default_meals`の書き込み | admin（既に画面あり） | 変更なし |

【設計提案】利用者名簿は**adminのみ編集可**とします。食数の日々の登録とは異なり、名簿の変更（新規入所・退所・区分変更）は施設側の管理業務であり、厨房職員が触る必要がないためです。

## 3.3 変更しないテーブル

`resident_groups`・`count_overrides`・`change_logs`・`profiles`・献立表/勤務表関連（`menu_imports`・`menu_items`・`shift_imports`・`shift_staff`・`shift_entries`・`shift_events`・`shift_date_events`・`shift_work_notes`）は変更なし。

# 4. 食数計算ロジックの変更

## 4.1 変更前（3段階の優先順位）

```
utilizer_eats(利用者, 日付, 食事区分) =
  kitchen_overrides に当日分の登録があれば その値        ← 厨房の緊急入力
  else meal_exceptions に登録があれば その値              ← Excel由来
  else 標準パターン[曜日, 食事区分]
```

## 4.2 変更後（2段階に簡素化）

```
utilizer_eats(利用者, 日付, 食事区分) =
  meal_exceptions に登録があれば その値    ← 管理者・厨房どちらの登録も同じテーブル
  else 標準パターン[曜日, 食事区分]

実食数(区分, 日付, 食) = COUNT(utilizer_eats = true)
※ count_overrides があれば上書き（管理者のみ・理由必須。従来通り）

調理必要数 = 利用者実食数合計 + 職員喫食数 + 来客喫食数
```

【設計提案】この簡素化により、`get_day_board`関数のロジックが大幅に短くなり、今後の保守が容易になります。また、これまで何度か発生した「優先順位の解釈違いによる不具合」のリスクも減ります。

# 5. 画面設計の変更

## 5.1 新設: 利用者管理画面（S9）

【要件指定】既存の`residents`・`resident_default_meals`（食形態・標準喫食パターンを含む）をそのまま流用し、アプリ内で管理できるようにします。

管理者画面に「利用者管理」を新設し、次の操作を可能にします。

```
┌────────────────────────────────────────────────────┐
│ 利用者管理                        [＋ 新規登録]      │
│ 区分: [すべて|男性入所|女性入所|男性GH|女性GH]      │ ← 絞り込み
├────────────────────────────────────────────────────┤
│ 氏名          区分      食形態      在籍   操作      │
│ 安田 彰       男性入所   －         在籍   [編集]    │
│ 伊丸岡 利史   男性入所   キ         在籍   [編集]    │
│ 鈴木 花子     女性入所   キ・ダ     在籍   [編集]    │
│ 高橋 幸子     女性GH     －         退所   [編集]    │
└────────────────────────────────────────────────────┘
```

**編集画面の項目**
- 氏名
- 区分（resident_groupsから選択）
- 食形態（刻み食／ダイエット食／粗みじん食／超みじん食のチェックボックス。複数可）
- 在籍状態（在籍／退所。退所日を記録）
- 標準喫食パターンへのリンク（既存画面を再利用）

**新規登録時の挙動**
- 区分に応じた標準喫食パターンを自動シード（入所=全21マスtrue／GH=平日昼のみtrue）。既存のExcel取込時のシード処理と同じロジックを流用します
- 【設計提案】退所は物理削除ではなく`left_on`への日付記録（論理削除）とします。過去の食数記録との整合性を保つためで、これは既存設計を踏襲します

## 5.2 変更: S5（欠食・臨時喫食登録）

| 項目 | 変更前 | 変更後 |
|---|---|---|
| 対象日 | 当日／翌日／翌々日の3択トグル | **任意の日付を選択可能**（カレンダーまたは日付ナビゲーション） |
| 書き込み先 | `kitchen_overrides` | `meal_exceptions` |
| 1タップ方式 | 氏名タップで即確定 | 変更なし（維持） |
| 事後取り消しトースト | あり | 変更なし（維持） |

【設計提案】日付制限をなくす代わりに、**選択中の日付を画面上部に大きく明示**し、「今日以外を編集中」の場合は背景色を変えるなどして、日付の取り違えを防ぐ視覚的な工夫を入れます。これは既存設計（§6.2）でS3に対して行っていた考え方をS5にも適用するものです。

## 5.3 変更: S6（職員・来客変更）

同様に、当日限定から任意の日付に対応させ、書き込み先を`daily_meal_extras`本体に変更します。

## 5.4 廃止: 食数Excelアップロード画面

管理者画面から「Excelアップロード」（食数表用）を削除します。**週間献立表アップロード・勤務表アップロードは残します。**

# 6. 移行手順

【設計提案】実データが稼働中のため、次の3段階に分けて進めることを推奨します。各段階ごとに開発用DBでの検証・PR・本番反映を行い、動作を確認してから次へ進みます。

## 段階A: 利用者管理画面の新設（リスク: 低）

- 利用者管理画面（S9）の実装
- `residents`のRLSをadmin書き込み可に変更
- **この段階では既存の食数計算・Excel取込には一切手を触れない**ため、万一問題があっても既存機能に影響しません

**完了条件**: 管理者画面から新規利用者を登録でき、標準喫食パターンが正しくシードされ、S2の食数計算に反映されること。

## 段階B: 食数のアプリ内直接編集を開放（リスク: 中）

- `meal_exceptions`・`daily_meal_extras`のRLSを変更（admin/kitchen とも日付制限なく書き込み可）
- S5・S6を任意日付対応に変更し、書き込み先を本体テーブルへ切り替え
- `get_day_board`の計算ロジックを2段階に簡素化
- **この時点では`kitchen_overrides`のデータも残っているため、移行前に登録された緊急入力が失われないよう、既存データを`meal_exceptions`へ移行するSQLを用意する**

**完了条件**: アプリ内で任意日付の欠食・臨時喫食・職員食・来客を登録でき、S2に即座に反映されること。既存のkitchen_overridesデータが正しく移行されていること。

## 段階C: 旧Excel機能の撤去（リスク: 中）

- 食数Excelのアップロード画面・パース処理・確認画面・競合確認の仕組みを削除
- `kitchen_overrides`・`kitchen_visitor_overrides`・`import_batches`テーブルを削除
- 関連するStorageバケット（`excel-imports`）を削除

**完了条件**: 不要なコード・テーブルが完全に除去され、既存機能（S2・S5・S6・献立表・勤務表）が問題なく動作すること。

【設計提案】段階Cは、段階Bが安定して1週間程度運用できたことを確認してから実施することを推奨します。万一の切り戻しに備え、削除は最後にまとめて行います。

# 7. 想定される問題点・確認事項

1. 【要確認】移行後、Excelファイルは貴施設で控えとして使い続けますか。システムからは参照されなくなるため、二重管理の手間を避けるなら使用をやめる判断もあり得ます（この点は運用のご判断です）。
2. 【設計上の注意】日付制限をなくすことで、厨房職員が誤って別日を編集するリスクは上がります。§5.2の視覚的な工夫に加え、変更履歴（S8）で「いつ・誰が・どの日付を変更したか」を追跡できるので、問題があれば履歴から特定できます。
3. 【設計上の注意】これまで「Excelが正」だったため、万一Supabaseのデータが失われても、Excelという別の記録が手元に残っていました。移行後はSupabaseが唯一の記録になるため、**バックアップの重要性が上がります**。以前保留にしたバックアップ方針（Supabase有料プランのPITR、または定期的な`pg_dump`の自動取得）を、この移行を機に改めて検討することを推奨します。
4. 【要確認】段階Bで既存の`kitchen_overrides`データを`meal_exceptions`へ移行しますが、現時点で`kitchen_overrides`は0件（本番確認済み）のため、実質的に移行対象はない見込みです。念のため段階B実施時に再確認します。

# 8. この変更で解消される課題

| 課題 | 解消される理由 |
|---|---|
| 変更のたびにExcel編集・アップロードが必要 | アプリ内で1タップ登録に |
| 厨房の入力が管理者の転記漏れで失われるリスク | 同じテーブルに直接書き込むため、そもそも転記という概念がなくなる |
| Excel取込の複雑なパース処理に起因する不具合 | 食数分のパース処理自体がなくなる |
| 「当日〜2日後」等の日付制限による不便 | 制限そのものが不要になる |
| 3段階の優先順位による計算ロジックの複雑さ | 2段階に簡素化 |

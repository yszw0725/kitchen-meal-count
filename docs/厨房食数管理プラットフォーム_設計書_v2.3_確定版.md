## 0.4 取り込み処理（アップロード時の挙動）

管理者画面の「Excelをアップロード」ボタン押下時、サーバーは次の順に処理します。

1. シートA・B・Cを読み取り、形式エラー（プルダウン外の値、日付不正等）があれば**取り込みを中断**し、該当行を具体的に示してエラー表示（サイレントな誤反映を防ぐ）
2. シートCの名簿を現在のDBの名簿と比較し、差分（新規追加・退所への変更）を算出
3. シートAの当日分について、**厨房が緊急入力した当日データと競合していないか**確認（§0.5）
4. 差分・競合をまとめた確認画面を表示 →「この内容で反映する」を管理者が押して初めて確定（自動では確定しない）
5. 確定後、Supabaseへ反映しRealtimeで厨房タブレットへ即時配信

## 0.5 緊急時（管理者不在時の厨房直接入力）の設計

【設計提案】通常運用（Excel入力→アップロード）を崩さず、緊急時だけ安全に共存させるため、厨房の当日入力は**Excel由来のデータとは別枠（オーバーレイ）として保存**します。

- 厨房が当日、S5から欠食・臨時喫食を直接登録すると、`kitchen_overrides` として保存され、即座に厨房タブレット表示に反映される（Excelには一切触れない）
- 該当セルには「厨房入力」の目立つバッジを表示し、管理者画面でも一覧で分かるようにする
- 管理者が次にExcelをアップロードした際、その日にkitchen_overridesが存在すれば、**上書き前に個別に確認画面を出す**（例:「8/13 昼食 田中太郎さんは厨房により欠食登録されています。Excelの内容で置き換えますか？／このまま残しますか？」）
- 管理者が「残す」を選んだ場合、その内容をExcel側にも反映するようメッセージで案内する（次回Excel編集時に転記していただく。自動でExcelファイルを書き換えることはしない＝Excel破損・書式崩れのリスクを避けるため）
- 一定期間（例: 7日）が経過した古いkitchen_overridesは自動的に「確定済み」として通常データに統合し、確認画面の対象から外す（無限に確認事項が溜まるのを防ぐ）

この方式により、通常時は完全にExcel任せ、緊急時だけ厨房が直接手を動かせ、かつ管理者が知らないうちにどちらかのデータが消えることを防げます。

## 1.4 食数の計算ロジック（裏計算シート）

【Excel事実】計算式を要約すると次の通りです。

```
男子部 実食数 = COUNTA(男子部名簿) − COUNTA(当日シートの男子部欠食者名欄)   … 在籍 − 欠食
女子部 実食数 = COUNTA(女子部名簿) − COUNTA(当日シートの女子部欠食者名欄)   … 在籍 − 欠食
GH1   実食数 = COUNTA(当日シートのGH1喫食者名欄)                        … 出席者を数える（加算方式）
GH2   実食数 = COUNTA(当日シートのGH2喫食者名欄)                        … 同上
利用者小計 = 男子部 + 女子部 + GH1 + GH2
合計食数（=調理必要数に相当） = 利用者小計 + 職員      ※来客は表上は行として存在するが、
                                                     裏計算の合計式には含まれていない（後述の課題）
```

- 【Excel事実】入所（男子部・女子部）は「**欠食を引く**」方式、GHは「**食べる人を書く**」方式で、**符号が逆**。
- 【Excel事実】解析週の実データでは、GHは平日昼のみ各5名（朝・夕は0）、週末は0。GHの標準は「平日昼のみ喫食」という運用が読み取れる。
- 【Excel事実】裏計算AA15に「欠食者が6人以上なら参照範囲を広げよ」というメモがあり、**欠食5名/枠が上限**という構造的制約がある。
- 【Excel事実】合計食数の式は `=SUM(C10,C11)`（利用者小計＋職員）であり、**来客セル（各曜日シート行29/33）は合計に参照されていない**。来客が発生した週は手動で辻褄を合わせていた可能性が高い（後述 §11 参照）。

## 1.5 個人別喫食集計（男子部／女子部／ニュース1・2シート）

【Excel事実】

- 各利用者×週21食（7日×3食）について、当日シートの名前欄を `COUNTIF` で検索し ○/× を判定。W列で「合計喫食回数」を集計。裏計算AA2に「合計出して、月間の喫食人数を出す」とあり、**月間の個人別喫食回数（実績集計・請求等の基礎資料と推測）**として使われている。
- 判定は**氏名文字列の完全一致**に依存。実データで不一致による誤集計を確認済み:
  - 月曜昼のGH2欄には「半田真由子（ダ）」と入力されているが、ニュース２シートの名簿は「半田真由子」のため × 判定（実際は喫食）。
  - 名簿「斉藤清美(大)」に対し入力「斉藤清美」も同様に不一致。
  - つまり**現行Excelの個人別集計は既に一部誤っている**。ID参照方式のDB化で根本解決できる（§12）。

## 1.6 食形態等の注記

【Excel事実】名簿の氏名に「（キ）（ダ）（粗）（超）（大）」等の注記が付与されている（例: 野口元太郎（ダ）、清水芳江（キ・ダ））。変更点シート・麺類盛付表では「きざみ／常食」の区別で戻り率を変えており、これらは**食形態・食事対応区分**と推測される。

- 【設計提案】Webでは氏名に注記を埋め込まず、利用者マスタの属性（食形態コード等）として分離して保持する。MVPでは表示のみ（任意）とし、盛付計算には使わない。**各記号の正確な意味は貴施設に確認が必要**（勝手に確定しません）。

# 3. Web化する機能 / Web化しない機能

## 3.1 Web化する（MVP）

【要件指定】§22の20項目すべて。日付管理／朝昼夕の食数管理／4区分／欠食者管理／実食数自動計算／職員食／来客／調理必要数／日付切替／欠食者詳細／厨房編集／管理者編集／リアルタイム同期／認証・権限／変更履歴／12インチUI／PWA。

## 3.2 Web化しない（現行運用を継続）

【要件指定】麺類盛付表（パスタ・木曜）／調理パンとロール／メンチカツバーガー／麺の種類／変更点（戻り率メモ）／各種印刷用盛付資料／週間献立表（掲示運用継続）。

【設計提案】ただし将来接続を見据え、次の2点だけ「余地」を残す。

- menus テーブル（日付×食事区分×献立名のみ）を将来追加できるスキーマ設計（MVPでは作らない）
- 麺類盛付で必要になる「刻み／常食の人数内訳」は、利用者マスタに食形態フィールドを持てば導出可能になる（MVPではフィールドのみ任意保持、計算はしない）

## 3.3 Web化により不要になるもの

- 曜日別7シートの複製・日付連鎖（→ DBの日付キー）
- 裏計算・早見表・欠食者リストシート（→ 導出ビューと画面表示）
- 欠食5名/枠の上限（→ 制限なし）
- 氏名文字列一致による個人集計（→ ID参照）
- 前日夕食の転記列（→ 日付切替で前日を見られる。トップ画面に前日夕を常設表示するかは要確認 → §11 未確認事項）

技術選定の補足:

- xlsxの解析はサーバー側（Next.js API Route / Vercel Serverless Function）で `SheetJS (xlsx)` を用いる。ブラウザ側で解析しない（大きめのファイルでもタイムアウトしにくく、解析ロジックを一箇所に保てる）
- アップロードされた元ファイルはSupabase Storageに保存し、後から「いつの時点のExcelを取り込んだか」を追跡できるようにする（監査・ロールバック用）
- 日付・タイムゾーンは引き続き Asia/Tokyo 固定

# 5. データベース設計（v2.0）

## 5.1 設計方針

- 【要件指定】区分はハードコーディングせずデータ管理。将来の増減に対応
- 【設計提案】実食数・調理必要数は**保存しない**（導出ビューで常に計算）
- 【設計提案】標準喫食パターン＋日次例外モデルで入所／GHの符号逆転を統一（§7）
- 【v2.0で追加】Excelアップロードの履歴・差分・厨房の緊急入力(kitchen_overrides)を独立したテーブルで管理し、通常データと明確に分離する

## 5.2 テーブル一覧（ER概要）


## 5.4 導出ビュー（実食数・調理必要数）

```sql
-- 区分×日付×食事区分ごとの人数
create view v_meal_counts as
select d.date, d.meal, g.id as group_id, g.short_name,
  count(*) filter (where eff.eats) as actual_count,          -- 実食数（導出）
  count(*)                          as enrolled_count,        -- 在籍数
  count(*) filter (where dm.eats and not eff.eats) as absent_count,  -- 欠食者数
  count(*) filter (where not dm.eats and eff.eats) as extra_count    -- 臨時喫食数
from (対象日×食事区分の系列) d
join residents r on 在籍判定(r, d.date)
join resident_groups g on g.id = r.group_id
join resident_default_meals dm on (r.id, extract(dow from d.date), d.meal)
left join meal_exceptions e on (r.id, d.date, d.meal)
cross join lateral (select coalesce(
    case e.type when 'absent' then false when 'present' then true end,
    dm.eats) as eats) eff
group by 1,2,3,4;
```

実装時は関数 `get_day_board(date)` （SECURITY DEFINER・SQL関数）として、区分別実食数（override があればそれを優先）＋職員＋来客＋調理必要数を1回で返す形にまとめる。インデックス:

```sql
create index on meal_exceptions (date, meal);
create index on meal_exceptions (resident_id, date);
create index on residents (group_id) where left_on is null;
create index on change_logs (created_at desc);
```

## 5.5 RLS方針

前提: すべてのテーブルで RLS 有効。`is_admin()` = profiles.role='admin' の判定関数（security definer）。

| テーブル | SELECT | INSERT | UPDATE | DELETE |
|---|---|---|---|---|
| resident_groups / residents / resident_default_meals | 認証済全員 | admin | admin | admin（原則は left_on による論理退所） |
| meal_exceptions | 認証済全員 | admin: 任意日 / kitchen: `date = current_date`のみ | 同上 | 同上 |
| daily_meal_extras | 認証済全員 | admin: 任意日 / kitchen: `date = current_date`のみ | 同上 | admin |
| count_overrides | 認証済全員 | admin | admin | admin |
| change_logs | 認証済全員（閲覧） | トリガのみ | 不可 | 不可 |
| profiles | 本人＋admin | admin | admin（本人はdisplay_nameのみ） | admin |

匿名アクセスは一切不可（要件§27「権限なしで書き換え可能な構造」の禁止をDB層で担保）。

- 調理必要数は各食カードの最上部に**96〜128pxクラスの数字**で表示（要件§17「数字を大きく」）
- 【変更】欠食者名（入所）・喫食者名（GH）は**常時、区分の数字のすぐ下に小さめの文字で表示**する。GHは「食べる人:」等のラベルを付けず**氏名のみ**を並べる（厨房職員には「GHは氏名＝喫食者」というルールが周知済みのため、ラベルは不要）。名前が多い場合は折り返し、上限は設けない（Excelの5枠制限を撤廃した設計と整合）

- 食形態バッジ（刻み／ダイエット／粗みじん／超みじん）は氏名の後ろに小さく添える（例: 「伊丸岡利史［刻み］」）。1画面の情報量が増えるため、食形態バッジは色分けせず淡いグレー系の小バッジに統一し、氏名の可読性を優先する

# 7. 食数計算ロジック（明文化）

## 7.1 モデル: 標準パターン＋例外

【設計提案】依頼文書§5〜6は全区分「在籍 − 欠食」ですが、Excelの実態はGHのみ「喫食者を書く（加算）」方式でした。両者を1つの規則で表現するため、次のモデルを提案します。

```
utilizer_eats(利用者, 日付, 食事区分) =
  例外(欠食/臨時喫食) が登録されていれば その値
  なければ 標準パターン[曜日, 食事区分]
```

- 入所利用者の標準 = 全食 true → 例外は「欠食」→ 結果は完全に「在籍 − 欠食」（要件§6の計算例をそのまま満たす）
- GH利用者の標準 = 平日昼のみ true → 平日昼は自動で5名が計上され、欠食登録で減る。標準外(朝・夕・週末)に食べる日だけ「臨時喫食」を1タップ登録
- 採用しない場合の代替案: GHも「在籍 − 欠食」に統一する（毎週、朝・夕・週末分の欠食を大量登録する運用になり非現実的なため非推奨。ただし要望があれば標準パターンを全true にするだけで同じ挙動になる = 本モデルは要件指定方式の上位互換）

## 7.2 計算式（v2.0: kitchen_overridesを最優先で反映）

```
utilizer_eats(利用者, 日付, 食事区分) =
  kitchen_overrides に当日分の登録があれば その値       ← 最優先（緊急入力）
  else 例外(meal_exceptions: 欠食/臨時喫食) が登録されていれば その値  ← Excel由来
  else 標準パターン[曜日, 食事区分]

在籍人数(区分, 日付)      = COUNT(residents WHERE 区分 AND entered_on ≤ 日付 ≤ left_on)
実食数(区分, 日付, 食)    = COUNT(utilizer_eats = true)
※ count_overrides があればその区分の実食数を最終的に上書き（管理者のみ・理由必須・履歴保存）

利用者実食数合計(日付, 食) = Σ 実食数(全区分)
調理必要数(日付, 食)       = 利用者実食数合計 + 職員喫食数 + 来客喫食数
```

【Excel事実との差分】現行Excelの合計式は来客を含んでいませんでした（来客は別ページの合計に手動で+加算する運用と伺っています）。Webでは上式の通り**来客を調理必要数の式に直接含めます**（依頼§9の指定に一致。手動の二重入力が不要になります）。

数値検証（解析週・月曜）: 朝 25+20+0+0+0職+0客=45 ✓、昼 25+20+5+5+0+0=55 ✓、夕 26+20+0+0+0+0=46 ✓（Excelの値と一致）。

# 8. 権限・セキュリティ設計（v2.0）

## 8.0 運用の考え方（v2.0で更新）

【要件指定・確定】本システムの主たるデータ入力者は**管理者（貴施設）**であり、引き続きExcelで日々の欠食・臨時喫食・職員食・来客・名簿を編集し、「Excelをアップロード」した内容がWeb・厨房タブレットに反映されます。厨房職員は基本的に**閲覧のみ**です。

管理者が休暇等で対応できない日、厨房側で数値を実態に合わせられないと厨房が困るため、厨房職員には**当日分のみ、Excelとは別枠（kitchen_overrides）への緊急直接入力**を許可します（§0.5）。翌日以降・名簿・職員来客の変更は厨房からは行えません。

| 操作 | 管理者 | 厨房職員 |
|---|---|---|
| 食数閲覧（任意日）・欠食者確認・履歴閲覧 | ○ | ○ |
| Excelアップロード（欠食・臨時喫食・名簿・職員食・来客の反映） | ○ | ✕ |
| 当日分の欠食・臨時喫食の緊急直接入力（kitchen_overrides） | ○（通常はExcel経由を推奨） | ○（フォールバック専用） |
| アップロード時の差分・競合確認 | ○ | ✕ |
| 実食数の手動修正（count_overrides） | ○ | ✕ |
| 区分・標準パターンの管理 | ○ | ✕ |
| ユーザー管理（招待・権限・無効化） | ○ | ✕ |

RLSは `admin: 全操作可 / kitchen: kitchen_overridesへのINSERT（当日分のみ）と全テーブルのSELECTのみ` とします。meal_exceptions・daily_meal_extras・residentsはExcel取込サーバー処理（service_role）以外からの書込みを禁止します。

## 8.1 厨房向けUIの簡素化方針（v1.2で追加）

高齢・電子機器不慣れな利用者を主対象とするため、S5（欠食登録）・S6（職員来客変更）を次の方針で設計し直します。

- **選択→トグル→確認の3段階を極力1〜2段階に圧縮**する。当初案（区分タブ→名前検索→対象食トグル→登録ボタン）は手数が多いため、**トップ画面（S2）から直接、区分カードをタップ→その区分の在籍者が写真・大きな文字の一覧で並び、氏名をタップするだけで「今日は欠食」を確定**する1タップ方式に変更（削除も同じ画面で再タップにより解除）。
- 文字入力・検索は要求しない（名前で探させない。在籍者数は最大26名程度のため、五十音一覧でスクロールのみで足りる）。
- 「朝／昼／夕」「終日欠食」の選択は、初期状態で**当日のうち未経過の食事に自動でチェック**（例: 昼の登録画面を開いた場合は昼のみ、まだ夕食前なら昼＋夕を初期選択）し、こちらから外す操作は最小限にする。
- ボタンの文言は漢字を減らし「休み」「食べる」等の平易な語を使う（「欠食」「臨時喫食」という業務用語はラベルとして残しつつ、操作ボタンは日常語にする）。
- 誤操作からの回復を容易にするため、直前の操作を画面上部に「たった今: 田中太郎さんを昼食お休みに登録しました［取り消す］」と5秒程度表示する（確認ダイアログの代わりに、事後の取り消しを用意し操作をシンプルに保つ）。
- 職員・来客（S6）は「−／数字／＋」の3要素のみで、長押し不可・1タップ1増減に統一。

- 認証: Supabase Auth（メール＋パスワード）。厨房タブレットは共用の厨房アカウント1つから開始し、必要になれば個人アカウント化（履歴の精度が上がる）。→ §11 未確認事項
- 権限はRLSでDB層強制。UIの出し分けは利便性のためであり防御はDBが担う
- 個人情報最小化: 氏名のみ保持（生年月日・住所等は持たない）。来客・職員は数値のみ（要件§7・8）
- セッション: PWAで長期セッション維持（refresh token）。共用端末のため自動ログアウトは設けない代わりに、書込みは全て履歴に残る
- 通信は常時TLS。Supabase の anon key はRLS前提で公開可、service_role key はサーバー側のみ

# 9. リアルタイム同期設計

- 唯一の正 = Supabase PostgreSQL（要件§14・§28）
- クライアントは表示中の日付の食数を `get_day_board(date)` で取得し、Supabase Realtime で `meal_exceptions` / `daily_meal_extras` / `count_overrides` / `residents` の postgres_changes を購読
- 変更イベント受信 → 表示中日付に関係すれば再取得（イベントのpayloadを直接信じず、必ずサーバー再計算値で描画 = 計算の正はDBのみ）
- 競合制御: 欠食は unique(resident, date, meal) により二重登録が構造的に不可能。職員・来客は「最後の書込みが勝つ」で実害なし（変更は履歴で追える）。厳密な同時編集ロックは導入しない（小規模運用に過剰）
- 切断時: Realtimeのステータスを監視し、画面右下に「● オンライン / ● オフライン（最終更新 09:32）」を常時表示。再接続時に自動で再取得
- タブレットは常時表示運用を想定し、visibilitychange / 定期(5分)ポーリングをフォールバックとして併用（Realtime切断の取りこぼし対策）

## オフライン時の編集について（要件§19の推奨案)

【設計提案】**MVPではオフライン編集を許可しない**ことを推奨します。

- 表示: Service Worker + ローカルキャッシュで「最後に取得した食数」を閲覧可能のまま維持し、オフラインバナーを明示
- 編集: 無効化（ボタンをグレーアウトし「通信復旧後に操作できます」）
- 理由: オフライン書込みキューを作ると、復旧時の順序・重複・「誰の値が正か」の問題が生じ、食数という「間違えると調理数を誤る」データでは危険がリターンに見合わない。厨房のネット断は一時的である前提なら、閲覧継続＋復旧後の編集で業務は成立する
- 将来、断続的な回線問題が実際に頻発する場合のみ、欠食登録に限定した送信キュー（unique制約で冪等）を検討

7. 【v2.3で追加】月次清算集計（食単価清算用）: 月初から月末までの朝・昼・夕それぞれの合計食数を出力する機能を追加スコープとして正式採用。合計食数には利用者実食数に加え職員食・来客数も含める（調理必要数と同じ考え方で確定）。GHの標準喫食パターン（平日昼は基本喫食）は清算金額に直結するため、この集計だけは簡易近似ではなく正確な計算ロジックを適用する。MVPのDB設計（§5.4の導出ビュー）をそのまま月次集計クエリに拡張すればよく、追加のテーブル設計は不要。

# 13. 4週間単位での運用について（ご質問への回答）

**可能です。設計変更は不要です。**

現行Excelは「週単位でシートをコピーし日付を書き換える」運用のため、7日という単位に構造的に縛られていますが、本設計は最初から**日付（date型）をキーとした連続データ**として扱っており、「週」という単位はどこにも存在しません（§5.3 `meal_exceptions`・`daily_meal_extras` はいずれも1行=1日×1食）。そのため：

- 4週間分をまとめて計画・入力しても、1日ずつ日をまたいでも、システムの動作は変わりません。日付選択（S3）で28日先まで見に行くことも、逆に4週間前を振り返ることも同じ操作です。
- resident_default_meals（標準パターン）は「曜日」に対して定義されるため、週が1つでも4つ連続しても同じ曜日には同じパターンが自動適用されます。4週間分を先回りして手入力する必要はありません。
- 唯一「4週」という言葉が現行Excelに出てくるのは、勤務表シートの `W1変` 等、**職員の勤務シフトが4週ローテーションで組まれている**箇所です（裏計算・職員食事変更ｼｰﾄが参照している外部ブック）。これは職員食数（daily_meal_extras.staff_count）の入力元の話であり、MVPでは職員食は手入力（現状0）のため今回の設計に影響しません。将来、勤務表との自動連携を行う際に「4週ローテーション」を踏まえた取込ロジックが必要になりますが、これも本体のデータモデルには影響しない別レイヤーの話です。

まとめると、「1週間ごとにシートを作り直す」というExcel特有の制約がWeb化によってなくなるため、4週間運用・8週間運用・通年運用のいずれも追加設計なしでそのまま成立します。
